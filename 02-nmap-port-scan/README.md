# Nmap Scan Analysis

## Scenario

This project looks at several packet captures generated by different Nmap scanning techniques.

Rather than focusing on the Nmap commands themselves, I wanted to see what each technique actually looks like on the wire and what clues would help me recognize the same behavior in a real capture.

The captures include:

* Standard port scanning
* ACK scanning
* Fragmented and spoofed scanning
* Idle / zombie scanning
* OS fingerprinting

## Environment

| Role                      | Address           |
| ------------------------- | ----------------- |
| Scanner                   | `192.168.100.103` |
| Primary Target            | `192.168.100.102` |
| Secondary Target / Zombie | `192.168.100.101` |

The role of `192.168.100.101` changes between captures. It acts as the zombie during the idle scan and as the target during the successful OS fingerprinting scan.

---

## Standard Port Scan

I started with the normal Nmap scan since it gave me the easiest baseline.

Filtering for SYN packets:

```text
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

immediately showed `192.168.100.103` sending probes to a large number of ports on `192.168.100.102`.

Examples included:

```text
23
25
135
143
554
1025
1723
3389
8080
8888
```

<p align="center">
  <img src="screenshots/01-standard-syn-scan.png"/>
  <br/>
  <em>Large number of SYN probes sent toward different destination ports</em>
</p>

The important part wasn't any individual packet. It was the overall pattern: one host sending SYN packets to many ports on another system in a very short period of time.

That is a much stronger indicator of scanning than looking at a single SYN packet by itself.

A filter I used to isolate it was:

```text
ip.src == 192.168.100.103 &&
ip.dst == 192.168.100.102 &&
tcp.flags.syn == 1 &&
tcp.flags.ack == 0
```

## ACK Scan

The ACK scan looked noticeably different.

Instead of beginning a connection with a SYN, the scanner sent packets to TCP/80 with only the ACK flag set.

```text
192.168.100.103 -> 192.168.100.102:80
Flags: ACK
```

<p align="center">
  <img src="screenshots/02-ack-scan.png"/>
  <br/>
  <em>ACK probes sent without an established TCP session</em>
</p>

That caught my attention because a normal TCP session should first go through:

```text
SYN
SYN/ACK
ACK
```

Here, the ACK packets appeared without that handshake.

The purpose of this type of scan is less about directly finding open ports and more about learning how a firewall or host responds to unexpected traffic.

Useful filter:

```text
tcp.flags.ack == 1 &&
tcp.flags.syn == 0 &&
tcp.dstport == 80
```

---

## Fragmented and Spoofed ACK Scan

The next capture made the ACK scan harder to interpret by combining two things:

* IP fragmentation
* Source IP spoofing

The real scanner was still:

```text
192.168.100.103
```

but the probes appeared to come from:

```text
192.168.100.101
```

toward:

```text
192.168.100.102
```

The packets were also split into small IPv4 fragments.

<p align="center">
  <img src="screenshots/03-fragmented-spoofed-scan.png"/>
  <br/>
  <em>Fragmented ACK probe using a spoofed source address</em>
</p>

I used:

```text
ip.flags.mf == 1 || ip.frag_offset > 0
```

to isolate the fragments.

This capture was a good reminder that looking at packets individually can be misleading. The TCP information may not be fully visible until the IP fragments are reassembled.

It also showed why a source IP shouldn't automatically be treated as proof of which machine actually generated the traffic.

## Idle / Zombie Scan

The idle scan was the most interesting capture because the scanner avoided directly probing the target with its own IP address.

The hosts were:

```text
Scanner: 192.168.100.103
Zombie:  192.168.100.101
Target:  192.168.100.102
```

The scanner repeatedly communicated with the zombie on TCP/2869 and watched the IPv4 Identification values in the responses.

Those values increased sequentially:

```text
120
121
122
123
124
125
...
```

<p align="center">
  <img src="screenshots/04-zombie-ipid.png"/>
  <br/>
  <em>Sequential IP ID values from the zombie host</em>
</p>

That predictable IP ID behavior is what makes the host useful for this technique.

During the actual port probe, the traffic appeared as:

```text
192.168.100.101 -> 192.168.100.102:80
```

rather than:

```text
192.168.100.103 -> 192.168.100.102:80
```

So from the target's perspective, the zombie appears to be the scanner.

Meanwhile, the real scanner continues checking the zombie and watching for changes in its IP ID sequence.

Useful filters:

```text
ip.addr == 192.168.100.101 && tcp.port == 2869
```

and:

```text
ip.src == 192.168.100.101 &&
ip.dst == 192.168.100.102 &&
tcp.dstport == 80
```

Looking at:

```text
Internet Protocol Version 4 -> Identification
```

was especially useful here.

## OS Fingerprinting

The last captures showed how Nmap tries to identify an operating system by sending unusual packets and comparing the target's responses.

This traffic looked different from a basic port scan because it included several unusual TCP flag combinations along with UDP and ICMP probes.

Examples included:

```text
SYN
ACK
FIN + PSH + URG
SYN + ECE + CWR
No TCP flags
FIN + SYN + PSH + URG
```

Those aren't typical application conversations. Nmap is intentionally testing how the target's TCP/IP stack reacts.

### Failed Attempt

The scan against:

```text
192.168.100.102
```

contained a large amount of probing, but the target didn't provide enough useful responses for reliable OS identification.

That made the capture useful because I could still see the fingerprinting behavior even though the fingerprint itself was unsuccessful.

### Successful Attempt

The scan against:

```text
192.168.100.101
```

produced more useful responses.

For example, the scanner sent a SYN to TCP/445 and received:

```text
SYN, ACK
```

showing that the port was open.

<p align="center">
  <img src="screenshots/05-os-fingerprint-open-port.png"/>
  <br/>
  <em>SYN/ACK response from TCP/445 during OS fingerprinting</em>
</p>

Other ports returned resets.

Having responses from both open and closed ports gave Nmap more information about how the host's network stack behaved.

## Scan Comparison

| Technique         | What Stood Out                                     |
| ----------------- | -------------------------------------------------- |
| Standard Scan     | Large number of SYN packets across many ports      |
| ACK Scan          | ACK packets without an established connection      |
| Fragmented Scan   | TCP probes split across IP fragments               |
| Spoofed Scan      | Source address does not represent the real scanner |
| Idle Scan         | Third-party host appears to perform the scan       |
| OS Fingerprinting | Unusual TCP, UDP, and ICMP probes                  |

## Useful Wireshark Filters

```text
# SYN probes
tcp.flags.syn == 1 && tcp.flags.ack == 0

# ACK-style probes
tcp.flags.ack == 1 &&
tcp.flags.syn == 0 &&
tcp.flags.reset == 0

# Scanner to primary target
ip.src == 192.168.100.103 &&
ip.dst == 192.168.100.102

# ACK scan of port 80
tcp.dstport == 80 && tcp.flags.ack == 1

# IPv4 fragmentation
ip.flags.mf == 1 || ip.frag_offset > 0

# Zombie traffic
ip.addr == 192.168.100.101 && tcp.port == 2869

# Zombie-to-target traffic
ip.src == 192.168.100.101 &&
ip.dst == 192.168.100.102 &&
tcp.dstport == 80

# SYN/ACK responses
tcp.flags.syn == 1 &&
tcp.flags.ack == 1

# TCP resets
tcp.flags.reset == 1
```

## Takeaway

The biggest thing I took from these captures was that reconnaissance is easier to recognize when looking at behavior across multiple packets rather than focusing on one packet at a time.

A standard scan produces an obvious burst of SYN probes, while techniques like ACK scanning, fragmentation, spoofing, and idle scanning change how that reconnaissance appears on the network.

OS fingerprinting stood out for a different reason: Nmap deliberately sends unusual packets to see how the target reacts.

Working through the captures made it much easier to understand what Nmap is actually doing behind the scenes and what those techniques would look like during packet analysis.
